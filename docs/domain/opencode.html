Overview OpenCode OpenAI v1 API Bridging

The OpenCode domain

OpenCode is an open-source AI coding agent: a program that plans and performs software engineering work in a project directory, driven by a conversational loop with a language model.

What OpenCode is

OpenCode runs locally and presents a terminal UI (TUI), but the TUI is only a client. The real system is a headless server that manages everything: conversation state, tool execution, permissions, and model calls. The server exposes an HTTP API plus a server-sent events stream, and a type-safe JS SDK (@opencode-ai/sdk) wraps it. Programmatic consumers never touch the TUI; they talk to the server over HTTP and listen to its event stream.

The central data model — and the vocabulary you must master — is: Project → Session → Message → Part, with a parallel event stream that reports everything as it happens.

Project
a directory / git worktree
Session
one conversation, bound to the project
Message
a user or assistant turn; the envelope
Part
typed content: text, tool, reasoning, …

Sessions

A session is a conversation with the agent, tied to one project directory. It is the OpenCode analogue of a “conversation” or “thread”.

A session is identified by an id and carries:

FieldMeaning
idUnique session identifier.
projectID, directoryThe project and working directory the session operates in. Tools run with this as their working directory.
parentIDOptional. Subagent invocations and forks create child sessions; a session with a parent is a child.
titleHuman-readable name, generated automatically by a background “title” agent.
time.created / time.updatedLifecycle timestamps (epoch ms).
versionSchema version of the session record.
summaryOptional aggregate: file additions/deletions/changes made during the session.
revertSet when a message (or part) has been reverted — a point-in-time rollback bookmark.

Session lifecycle

  • Create — a new empty session; optionally with a parentID to attach it as a child.
  • Prompt — post a user message; the agent responds. This is the core operation (see Messages).
  • Abort — stop the agent mid-run; the in-flight assistant message is finalized with an abort error.
  • Revert — roll the session back to a message (or even a single part), undoing later work and restoring the working tree to a snapshot.
  • Fork — branch a copy of the session at a given message.
  • Summarize / compact — condense history when context gets long (see Compaction).
  • Delete — remove the session and its data.

Session status

A session is in one of three states, published over the event stream as session.status:

StatusMeaning
idleNo agent activity; safe to prompt.
busyThe agent is running — generating, streaming, or executing tools. Additional prompts may be queued or rejected depending on the implementation.
retryAn error occurred; the run is pausing (with an attempt counter and delay) before retrying the request.

A separate session.idle event fires when a run completes. Consumers that need to know “is it done?” watch for the busy → idle transition.

Messages

A message is one turn in a session, with a role of user or assistant. Messages are envelopes: the visible content lives in the parts attached to them. A message is identified by id and belongs to one sessionID.

User messages

Record what the human (or a programmatic client) said:

FieldMeaning
role: "user"Message type discriminator.
agentName of the agent that will handle the response.
model{ providerID, modelID } — which model will be used for the reply.
systemOptional per-prompt system prompt override.
toolsOptional map of tool name → enabled flag, overriding the agent’s default tool set for this prompt.
time.createdWhen the user sent it.

Assistant messages

Record one full agent run — which may span many model calls:

FieldMeaning

parentIDId of the user message this is a reply to.
providerID, modelIDWhich provider/model actually produced the response.

time.created / time.completedRun start and end.
costMonetary cost of the run in dollars.
tokensUsage: input, output, reasoning, and cache.read / cache.write.
finishWhy the run ended (equivalent to a finish reason: stopped, max length, aborted, …).
errorOptional structured error recording why the run failed (see Errors): provider auth failure, unknown error, output-length exceeded, aborted, or API error with status code and body.

The prompt operation

Sending a prompt to a session (POST /session/:id/message or the SDK’s session.prompt) does the following:

  1. Creates a user message containing the provided parts (text, files, agent mentions, …).
  2. Creates an assistant message as its reply and marks the session busy.
  3. Runs the agentic loop (see Steps) until the agent finishes.
  4. Returns the finalized assistant message with its parts.

A variant, noReply / prompt-async, only records the user message (context injection, e.g. by plugins) without triggering a run. When noReply is true, the session stays idle.

Parts

A part is a typed unit of content inside a message, identified by id and addressed as sessionID / messageID / partID. Every message’s parts form an ordered log of what happened. Streaming works at part granularity: parts are created, appended to, and updated in place as the run progresses.

The part catalog

Part typeContentsWhen it appears
text text string; optional synthetic (tool-generated, not model output) and ignored flags The core visible content. Streamed incrementally via deltas.
reasoning text — the model’s chain of thought Models that expose reasoning traces; distinct from the final answer.
file mime, filename, url; optionally a source (text range or symbol) in a file Attachments: images, PDFs, documents the user or agent attached. Files can also be attached to tool results.
tool callID, tool name, input JSON, state, output/error Every tool invocation. The heart of tool calling (see below).
step-start optional snapshot id of the working tree Start of one model invocation within the agentic loop.
step-finish reason (why the step ended), cost, tokens, optional snapshot End of a step. Between step-start and step-finish lies one model round trip.
snapshot snapshot id Checkpoint of the working tree, enabling revert.
patch hash, files touched Records that file edits were applied.
agent name, optional source range of the @-mention in the user text Marks that a user message @-mentioned (invoked) a specific agent.
subtask prompt, description, agent Records that a subagent was spawned from the session (see child sessions).
retry attempt number, error A failed model request being retried.
compaction auto — whether compaction was automatic Marks that the session was compacted (see Compaction).

Streaming at the part level

As the model generates, the server emits message.part.updated events for the assistant message’s parts. For text and reasoning parts each event carries a delta — the newly produced characters — which consumers append to the part’s text. Tool parts transition through states rather than accumulating deltas. This event-level streaming is the OpenCode equivalent of SSE token streaming in OpenAI’s protocol.

Tool calling

OpenCode is an agentic system: the model does not merely answer, it uses tools — running shell commands, editing files, searching the codebase, fetching web pages — and iterates. The built-in tool set includes bash, read, write, edit, apply_patch, glob, grep, list, task (subagent invocation), webfetch, websearch, todowrite, question, and skill. Tools can also come from MCP servers or custom definitions.

The tool part

Every invocation is represented by a tool part:

FieldMeaning
callIDUnique id of this call, generated by the server.
toolTool name, e.g. bash.
inputFree-form JSON object of the call arguments (e.g. {"command": "ls"}).
stateLifecycle state, below.
titleHuman-readable summary of what the tool is doing (set while running and on completion).
outputString result when completed.
errorError message when the call failed.
attachmentsOptional file parts produced by the tool (e.g. a screenshot taken by bash).

Tool state lifecycle

pending
call requested by the model, not yet started
running
executing; has start time and title
completed
successful; output, title, duration
error
failed; error message, duration

Long-running tools (like bash) can be streamed: the running state carries metadata that is updated while the process produces output.

Permissions

Tools are gated by permissions, per agent: ask (prompt the user for approval), allow (run without asking), or deny (never run). When a tool needs approval, the server emits a permission.updated event with a permission request containing a title, the pattern matched, and metadata. The consumer responds via the permissions endpoint (session.permissions), optionally with remember to persist the choice. This is a first-class, synchronous decision point inside an otherwise asynchronous run.

Steps and the agentic loop

One “assistant run” is rarely a single model call. The server drives a loop:

1. Call the model
history + tools → step-start
2. Tool calls?
execute tools → feed results back
3. Finished?
text reply → step-finish, run done

Each iteration is a step, delimited by step-start and step-finish parts. The step-finish reason records whether the model ended the turn, hit a tool-call boundary, was interrupted, or hit an output limit. The assistant message and its parts accumulate across all steps; the run ends with a session idle event.

Agents may be configured with a maximum step count; when exhausted, the agent is forced to summarize its work in a text response instead of calling more tools.

The event stream

The server exposes a server-sent events (SSE) stream at /event. It is the single source of truth for live state. Events are discriminated by type and carry a typed properties payload. The events most relevant to conversation flow:

The first event on a fresh connection is server.connected. Events are the streaming mechanism: a consumer that wants “OpenAI-style token streaming” from OpenCode translates message.part.updated deltas into response chunks.

Agents

An agent is a configured persona: a system prompt, a model, a tool set, and permissions. There are two kinds:

KindRoleExamples
Primary Holds the main conversation with the user. The user switches between them (e.g. with Tab in the TUI). build (all tools), plan (analysis only, changes gated by permissions)
Subagent Focused workers invoked by a primary agent (via the task tool) or @-mentioned by the user. Each runs in its own child session. general, explore (read-only codebase research), scout (external research)

Agent configuration includes temperature, top_p, description (when to use it), mode (primary/subagent/all), maxSteps, and a permission block. Unknown configuration keys pass through to the provider as model options.

Providers and models

OpenCode is model-agnostic. A provider (Anthropic, OpenAI, OpenCode Zen, Ollama, any custom endpoint) exposes models, each addressed as providerID/modelID (e.g. anthropic/claude-sonnet-4-20250514).

Models declare capabilities that matter to an adapter:

CapabilityMeaning
temperature / reasoningWhether the model supports sampling temperature and reasoning output.
attachmentWhether file/image attachments are accepted.
toolcallWhether the model supports tool calling.
input / outputSupported modalities: text, audio, image, video, pdf.
limit.context / limit.outputContext and output token budgets.
costPer-token pricing for input/output and cache reads/writes.

The server exposes the configured providers and models over /config/providers and /provider, so consumers can discover what is available rather than hardcoding it.

Compaction

Long sessions eventually exceed a model’s context window. When that happens, OpenCode performs compaction: a background agent summarizes the conversation so far, and the summarized history replaces the old messages. A compaction part and a session.compacted event mark the transition, and the condensed context is what subsequent model calls see. For an external consumer this looks like the session’s history suddenly shrinking — an adapter should not be surprised by it.

Errors

OpenCode reports failures as a single structured error: an object discriminated by its type field, so consumers branch on what kind of failure happened rather than parsing prose. The same record shape is reused everywhere the agent loop can fail: on the assistant message, inside retry parts, and on the event stream.

The error shape

FieldMeaning
typeDiscriminator — the kind of error; one of auth, unknown, output, abort, api (below).
messageHuman-readable description of what went wrong.
statusHTTP status code. Present when the failure arrived over HTTP (the api kind).
bodyRaw payload from the failing endpoint. Present together with status.

Error kinds

typeMeaningRetryable
auth Provider authentication failed: missing, invalid, or rejected API key or credentials. No — the key must be fixed, not the request.
unknown Something failed that could not be classified. Possibly; a retry may be the only option.
output The model’s response exceeded the model’s output length limit. No — the run must be restarted with less history or a different step plan.
abort The run was stopped mid-flight — an explicit abort, or the client disconnected. The in-flight assistant message is finalized with this error. No — the stop was intentional.
api The provider returned an HTTP error; carries status and body (e.g. 429 rate limit, 5xx outage). Typically — depends on the status code.

Where errors appear

  • Assistant message error with finish: "error" — terminal. The whole run ended in failure; this record is the authoritative account of why, and it is what a consumer shows to its user.
  • retry parts — transient. A model request failed but will be retried: the part records the attempt number and the error that triggered the retry. The session status is retry while the run pauses between attempts.
  • tool part error / error state — a tool call failed. Unlike model failures this is not an end-of-run problem: the failure text is returned to the model as the tool result and the agent keeps going.
  • session.error event — session-scope failures announced over the event stream, carrying the same structured error.
  • HTTP errors from the server’s own API — distinct. When a consumer’s request is malformed, the server answers over HTTP with a status code and error body, like any REST API. These are protocol errors, not agent errors, and do not appear in the data model.

Fail → retry → resolve

A failing model request is not an instant end. The server marks the session retry, records a retry part per attempt, and waits a delay before trying again. Either the retry succeeds and the run proceeds, or the server gives up and the run terminates with a final message whose finish is "error" and whose error field holds the structured record.

request fails
a structured error is produced
session pauses
status “retry”; retry part with attempt N and delay
recovers
the run continues; the retries stay in history
gives up
finish: “error” + message.error
// The canonical record
{ "type": "auth", "message": "authentication failed" }

// A provider HTTP failure — status and body included
{ "type": "api",
  "status": 429,
  "body": { "error": { "type": "rate_limit_error", "message": "Rate limit exceeded" } } }

// Terminal — the run failed, surfaced on the assistant message
{ "id": "msg_08", "role": "assistant", "finish": "error",
  "error": { "type": "output", "message": "The response exceeded the output limit" } }

// Transient — a request being retried
{ "type": "retry", "attempt": 2,
  "error": { "type": "api", "status": 500 } }

Other surfaces

  • Slash commands (/init, /undo, …) — templated prompts executed in a session via the commands endpoint; they produce ordinary messages.
  • Todos — the agent’s live task list for a session (session/:id/todo), updated via todo.updated events.
  • Snapshots & revert — file-tree checkpoints that make undo possible; snapshot and patch parts record edit history.
  • Shell/PTY — the server can create interactive pseudo-terminals for running commands that need stdin or long-lived output.
  • File & search APIs — file.read, find.text, find.files, find.symbols — the same facilities the agent’s tools use.
