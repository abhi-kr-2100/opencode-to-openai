OpenCode & the OpenAI v1 API

Domain reference for bridging a local OpenCode installation to the OpenAI v1 API protocol. These guides describe the two domains on their own terms and the conceptual seams between them — they are written to inform an implementation, not to describe one.

The two domains

An OpenAI-compatible server is a program that speaks the HTTP + JSON wire protocol that OpenAI’s public API exposes under /v1. Thousands of tools — SDKs, wrappers, agents, and LLM gateways — are built against this one protocol, so any server that speaks it can stand in for OpenAI’s hosted service. OpenCode is a different kind of system entirely: a local, terminal-first agentic coding product. It exposes its own HTTP/SSE server and a JS SDK whose data model is built around sessions, messages, and parts.

These guides cover the vocabulary and mechanics of both domains and the translation problem between them. The full picture looks like this:

OpenAI client
SDK / chat UI / agent framework
Adapter
/v1 endpoints → OpenCode server calls
OpenCode
session engine, tools, events
Local model / provider
Anthropic, OpenAI, Ollama, Zen …

Who this is for

Anyone implementing or extending an adapter that exposes OpenCode behind an OpenAI-shaped API. It assumes no prior knowledge of either system. Implementers should read all three guides in order; a quick refresher on one system alone requires only its dedicated guide.

Glossary

Each term is tagged with its domain (OpenCode / OpenAI), followed by a worked example and, where useful, a visualization.

Session OpenCode

OpenCode’s unit of conversation: one thread of user prompts and agent responses, bound to a project directory. Carries a title, timestamps, a model, an agent, and possibly a parent session.

Example
{
  "id": "sess_01",
  "directory": "/home/me/app",
  "title": "Add auth to /settings",
  "time": { "created": 1754000000000, "updated": 1754000123000 }
}

Message OpenCode

A single turn in an OpenCode session, of role user or assistant. Messages are envelopes: the actual content lives in their parts. Messages also carry metadata such as the model used, token counts, cost, finish reason, and errors.

Example — user and assistant messages
// user message
{ "id": "msg_02", "sessionID": "sess_01", "role": "user",
  "agent": "build",
  "model": { "providerID": "anthropic", "modelID": "claude-sonnet-4-20250514" } }

// assistant message (envelope; content lives in parts)
{ "id": "msg_07", "sessionID": "sess_01", "role": "assistant",
  "parentID": "msg_02",
  "providerID": "anthropic", "modelID": "claude-sonnet-4-20250514",
  "finish": "stop", "cost": 0.0042,
  "tokens": { "input": 4120, "output": 500, "reasoning": 120 } }
Part OpenCode

A typed unit of content inside a message. OpenCode has parts for text, reasoning traces, files, tool calls, step boundaries, snapshots, patches, and more. Parts are the fine-grained currency of streaming.

Example — a text part and a tool part
{ "id": "part_01", "sessionID": "sess_01", "messageID": "msg_07",
  "type": "text", "text": "I'll investigate the flaky test." }

{ "id": "part_03", "sessionID": "sess_01", "messageID": "msg_07",
  "type": "tool", "callID": "call_01", "tool": "bash",
  "input": { "command": "npm test" },
  "state": { "status": "completed", "output": "PASS 12/12" } }

Tool call OpenCode OpenAI

The act of the model requesting an external operation (run a command, edit a file, fetch a URL, …). In OpenCode a tool part records the call id, tool name, JSON input, and a lifecycle of pending → running → completed/error. In the OpenAI protocol the same act is split across an assistant tool_calls field and a subsequent tool role message.

Example — the same call in both dialects
// OpenCode: one part that the server executes
{ "type": "tool", "callID": "call_01", "tool": "bash",
  "input": { "command": "npm test" },
  "state": { "status": "completed", "output": "PASS 12/12" } }

// OpenAI: the client must execute it and feed the result back
{ "role": "assistant", "content": null, "tool_calls": [{
    "id": "call_01", "type": "function",
    "function": { "name": "bash", "arguments": "{\"command\":\"npm test\"}" } }] },
{ "role": "tool", "tool_call_id": "call_01", "content": "PASS 12/12" }
Visualization — tool part state machine

Step OpenCode

One model invocation within an agentic loop. A response that ends in tool calls triggers another step; a response that “finishes” ends the loop. OpenCode marks steps with step-start and step-finish parts.

Example — step-finish part
{ "type": "step-finish", "reason": "tool_calls",
  "cost": 0.0011,
  "tokens": { "input": 4120, "output": 380, "reasoning": 120 } }

Agent OpenCode

A configured persona in OpenCode with its own system prompt, model, and tool permissions. Primary agents (build, plan) hold the main conversation; subagents (general, explore, …) are invoked for focused work.

Example — agent configuration
{
  "agent": {
    "code-reviewer": {
      "description": "Reviews code for quality and potential issues",
      "mode": "subagent",
      "model": "anthropic/claude-sonnet-4-20250514",
      "prompt": "You are a code reviewer. Focus on security and maintainability.",
      "permission": { "edit": "deny" }
    }
  }
}
Event bus OpenCode

OpenCode’s real-time channel. A server-sent events stream emits message.updated, message.part.updated (with streaming deltas), session.status, permission.updated, and similar events.

Example — three events as received over SSE
data: {"type":"message.part.updated","properties":{
  "part":{"id":"part_02","type":"text","text":"The fix is simple: "},
  "delta":"The fix is simple: "}}

data: {"type":"message.part.updated","properties":{
  "part":{"id":"part_02","type":"text","text":"The fix is simple: bump the timeout."},
  "delta":"bump the timeout."}}

data: {"type":"session.idle","properties":{"sessionID":"sess_01"}}

Error OpenCode

OpenCode’s structured failure record, discriminated by a type field: one of auth (bad credentials), unknown (unclassified), output (exceeded the output limit), abort (run stopped mid-flight), or api (provider HTTP failure, carrying status and body). The record surfaces on the assistant message (authoritative, with finish: "error"), transiently in retry parts, as a string on failed tool calls, and over the session.error event.

Example — the same kind of failure, at two lifecycle points
// transient: a request being retried
{ "type": "retry", "attempt": 2,
  "error": { "type": "api", "status": 429,
             "body": { "error": { "message": "Rate limit exceeded" } } } }

// terminal: the run finally failed
{ "role": "assistant", "finish": "error",
  "error": { "type": "api", "status": 429 } }

Distinct from OpenAI’s error contract, where failures are HTTP statuses with an error object in the body (see the OpenAI guide).

Chat Completions OpenAI

OpenAI’s classic endpoint (POST /v1/chat/completions). Accepts a list of messages and returns a completion, either in one response or as a stream of SSE chunks. The de-facto standard that OpenAI-compatible servers reproduce.

Example — a request
curl -X POST https://api.openai.com/v1/chat/completions \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-4o",
    "messages": [{ "role": "user", "content": "Say hello" }],
    "stream": true
  }'
Content part OpenAI

An element of a message’s content array in the OpenAI protocol: text, an image URL, audio, … Not to be confused with OpenCode’s part model, though they play a similar role.

Example — array content with two parts
"content": [
  { "type": "text", "text": "This is the failing test:" },
  { "type": "image_url", "image_url": {
      "url": "data:image/png;base64,iVBORw0KGgo..." } }
]
Streaming chunk OpenAI

One SSE data: frame of a streaming Chat Completion. Each chunk carries a choices array with a delta (partial role/content/tool-call data) and, for the final chunk, a finish_reason.

Example — the stream, chunk by chunk
data: {"id":"chatcmpl_01","object":"chat.completion.chunk","choices":[
  {"index":0,"delta":{"role":"assistant"},"finish_reason":null}]}

data: {"id":"chatcmpl_01","object":"chat.completion.chunk","choices":[
  {"index":0,"delta":{"content":"Paris"},"finish_reason":null}]}

data: {"id":"chatcmpl_01","object":"chat.completion.chunk","choices":[
  {"index":0,"delta":{},"finish_reason":"stop"}]}

data: [DONE]

Delta OpenCode OpenAI

The increment of new content carried by one event in a stream — never the whole message. In OpenCode, each message.part.updated event carries a delta string that the consumer appends to the part’s growing text. In the OpenAI protocol, each streaming chunk’s delta object holds the newly produced fragment of role, content, or tool-call data. Both dialects are incremental: everything before the delta is already known, so accumulating deltas in order reconstructs the full output.

Example — the same sentence, delta by delta, in both dialects
// OpenCode: message.part.updated events
delta: "The fix"
delta: " is simple:"
delta: " bump the timeout."

// OpenAI: chat.completion.chunk deltas
"delta": { "role": "assistant" }
"delta": { "content": "The fix" }
"delta": { "content": " is simple:" }
"delta": { "content": " bump the timeout." }
Visualization — deltas accumulate into the full text

Caveat for implementers: deltas must be consumed in order, and a delta always updates the part or message it belongs to — an out-of-order delta corrupts the accumulated text.

SSE OpenCode OpenAI

Server-Sent Events, the HTTP-based streaming format (text/event-stream) used by both the OpenAI protocol and OpenCode’s event stream.

Example — raw wire format
data: {"type": "session.status", "properties": { "sessionID": "sess_01", "status": "busy" }}

data: {"type": "message.part.updated", "properties": { "delta": "The fix is simple: " }}
Tool OpenCode OpenAI

An operation exposed to the model with a name, description, and JSON Schema parameter specification. OpenCode ships tools like bash, edit, read, and webfetch; the OpenAI protocol declares them in the request tools array.

Example — declaring a tool
"tools": [{
  "type": "function",
  "function": {
    "name": "bash",
    "description": "Run a shell command in the project directory",
    "parameters": {
      "type": "object",
      "properties": { "command": { "type": "string" } },
      "required": ["command"]
    }
  }
}]
Finish reason OpenCode OpenAI

Why the model stopped generating: stop, length, tool_calls, content_filter. In OpenCode this surfaces as the message-level finish field and the step-finish part reason.

Example — final response fragment
"choices": [{
  "index": 0,
  "message": { "role": "assistant", "content": "Tests pass now." },
  "finish_reason": "stop"
}]
Usage OpenCode OpenAI

Token accounting attached to a response. The OpenAI protocol reports prompt_tokens, completion_tokens, and total_tokens; OpenCode tracks input, output, reasoning, and cache read/write tokens plus a dollar cost.

Example — OpenAI usage object
"usage": {
  "prompt_tokens": 4120,
  "completion_tokens": 500,
  "total_tokens": 4620
}
