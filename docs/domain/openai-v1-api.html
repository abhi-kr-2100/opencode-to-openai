The OpenAI v1 API

A plain-HTTP, JSON wire protocol for talking to language models. Because an enormous ecosystem of SDKs, agents, and gateways is built against it, the “v1 shape” is effectively a standard — any server that reproduces it faithfully is interchangeable with OpenAI’s hosted API.

What the API is

OpenAI’s public API lives at https://api.openai.com/v1, is authenticated with a Bearer token (Authorization: Bearer <key>), and speaks JSON over HTTP. Two generations of completion endpoints exist:

EndpointStyleStatus
POST /v1/chat/completionsMessages in → completion out (single or streamed)Classic; the de-facto compatibility target that “OpenAI-compatible” servers implement.
POST /v1/responsesConversation state in → typed output items outNewer, evolving; most OpenAI-compatible servers target Chat Completions instead.

This guide focuses on Chat Completions — the shape an OpenAI-compatible adapter must reproduce — and touches on GET /v1/models and the error contract.

Chat Completions — the request

A request to POST /v1/chat/completions looks like:

{
  "model": "gpt-4o",
  "messages": [
    { "role": "system", "content": "You are a helpful assistant." },
    { "role": "user",   "content": "What is the capital of France?" }
  ],
  "temperature": 0.7,
  "max_completion_tokens": 1024,
  "stream": false
}

Request fields

FieldMeaning
modelModel identifier string. Required.
messagesOrdered conversation history. Required.
tools, tool_choiceTool/function declarations and selection policy (see Tool calling).
temperature, top_pSampling controls; typically 0–2 / 0–1. Many compatible servers only accept 0–1.
max_completion_tokensHard cap on generated tokens. The newer name for max_tokens, which is still accepted by many servers.
stopString or array of strings that end generation.
streamtrue switches the response from a single JSON body to an SSE stream of chunks.
stream_optionse.g. {"include_usage": true} to get a final usage chunk in streams.
nNumber of completions to generate (usually 1; rarely supported by compatible servers).
response_format{"type": "json_object"} or {"type": "json_schema", "json_schema": {...}} to force structured output.
parallel_tool_callsWhether the model may emit multiple tool calls per message (default true).
seedBest-effort determinism hint.
logit_bias, presence_penalty, frequency_penaltyToken-level and repetition controls; optional.
userFree-form client identifier for abuse tracking.

Messages and roles

The conversation is a list of messages. Each has a role and a content that is either a string or an array of content parts.

RoleWho speaksNotes
systemThe applicationTop-level instructions; conventionally the first message. Some models treat it as a developer message.
developerThe applicationNewer role name for system-style instructions (o-series models).
userThe end userThe actual prompt.
assistantThe modelPrior model replies — including any tool_calls it made. Some models also expose reasoning_content here.
toolThe tool executorResult of a tool call; must include tool_call_id matching the assistant’s call.

An assistant message with tool calls and the tool results that follow look like:

{
  "role": "assistant",
  "content": null,
  "tool_calls": [{
    "id": "call_abc123",
    "type": "function",
    "function": {
      "name": "get_weather",
      "arguments": "{\"city\": \"Paris\"}"
    }
  }]
},
{
  "role": "tool",
  "tool_call_id": "call_abc123",
  "content": "{\"temp\": 21, \"condition\": \"clear\"}"
}

Content parts

When content is an array, each element is a typed part:

Part typeShapeNotes
text{"type": "text", "text": "..."}Plain text; may carry annotations.
image_url{"type": "image_url", "image_url": {"url": "..."}}Image by URL or base64 data URI; optional detail level.
input_audio{"type": "input_audio", "input_audio": {"data": "base64", "format": "wav"}}Audio input; format-specific.
refusalPresent on assistant content when the model declinedNot a user-supplied part; surfaced in responses.

Note the naming collision: the OpenAI protocol calls these content parts, while OpenCode has its own richer part model. They play the same structural role (typed content inside a message) but are different vocabularies. See Bridging.

Tool calling

Tool calling (a.k.a. function calling) lets the model request that the application do something. It is a multi-round protocol between client and server — the server never executes tools itself.

1. Declare tools

"tools": [{
  "type": "function",
  "function": {
    "name": "get_weather",
    "description": "Current weather for a city",
    "parameters": {
      "type": "object",
      "properties": { "city": { "type": "string" } },
      "required": ["city"]
    }
  }
}]

parameters is a JSON Schema object. strict: true requests strict schema adherence.

2. Choose a policy

  • tool_choice: "auto" — model decides whether to call tools (default).
  • tool_choice: "none" — never call tools.
  • tool_choice: "required" — must call a tool.
  • tool_choice: {"type": "function", "function": {"name": "get_weather"}} — force a specific tool.

3. Run the loop

The client drives the loop — the server is stateless between requests:

  1. Send history + tools.
  2. If the assistant message contains tool_calls, execute each call application-side.
  3. Append the assistant message and one tool message per call (tool_call_id links result → call).
  4. Send the extended history again. Repeat until the model replies without tool calls.
Request
history + tools
Response
text and/or tool_calls
Execute
client runs the tools
Feedback
append tool messages → loop

Tool-call arguments are always a JSON string, parsed by the client. parallel_tool_calls means one assistant message can carry several calls; each gets its own id and its own tool result message.

Streaming

With "stream": true the server responds with Content-Type: text/event-stream (SSE): a sequence of data: frames, each a JSON object, terminated by a data: [DONE] frame. 

data: {"id":"chatcmpl-1","object":"chat.completion.chunk","created":1700000000,
       "model":"gpt-4o","choices":[{"index":0,
         "delta":{"role":"assistant","content":""},
         "finish_reason":null}]}

data: {"id":"chatcmpl-1","object":"chat.completion.chunk","created":1700000000,
       "model":"gpt-4o","choices":[{"index":0,
         "delta":{"content":"The capital of France"},
         "finish_reason":null}]}

data: {"id":"chatcmpl-1","object":"chat.completion.chunk","created":1700000000,
       "model":"gpt-4o","choices":[{"index":0,
         "delta":{},"finish_reason":"stop"}]}

data: [DONE]

Chunk anatomy

FieldMeaning
id, object: "chat.completion.chunk"Identifiers; the id is shared across all chunks of one completion.
created, modelMetadata.
choices[]Per-completion streams (one choice per stream normally). Each has an index.
deltaThe new content of this chunk: role on the first chunk, then content text, then tool_calls fragments for tool-call streams.
finish_reasonnull while streaming; set on the final chunk: stop, length, tool_calls, content_filter, function_call.
usageOnly on the final chunk when stream_options.include_usage is set (with empty choices).

Streaming tool calls

Tool calls stream as fragmented deltas; clients accumulate them by index:

{"delta":{"tool_calls":[{"index":0,"id":"call_abc","type":"function",
   "function":{"name":"get_weather","arguments":""}}]}}
{"delta":{"tool_calls":[{"index":0,"function":{"arguments":"{\"ci"}}]}}
{"delta":{"tool_calls":[{"index":0,"function":{"arguments":"ty\": \"Paris\"}"}}]}}

Note the first chunk carries the call id and name; subsequent chunks carry only arguments fragments. Some models also stream reasoning_content in a separate delta field before the answer.

Non-streaming response

With "stream": false, one JSON body comes back:

{
  "id": "chatcmpl-1",
  "object": "chat.completion",
  "created": 1700000000,
  "model": "gpt-4o",
  "choices": [{
    "index": 0,
    "message": {
      "role": "assistant",
      "content": "Paris is the capital of France."
    },
    "logprobs": null,
    "finish_reason": "stop"
  }],
  "usage": {
    "prompt_tokens": 14,
    "completion_tokens": 8,
    "total_tokens": 22,
    "prompt_tokens_details": { "cached_tokens": 0 },
    "completion_tokens_details": { "reasoning_tokens": 0 }
  }
}

The message here is the exact object that must be echoed back into the next request’s messages (with its tool_calls, if any).

Models endpoint

GET /v1/models
→ { "object": "list", "data": [ { "id": "gpt-4o", "object": "model", "created": ..., "owned_by": "openai" } ] }

Clients use this to list and validate model ids. An OpenAI-compatible server should return its own available models here.

Errors

Errors are JSON with a consistent envelope:

{
  "error": {
    "message": "Incorrect API key provided",
    "type": "invalid_request_error",
    "param": null,
    "code": "invalid_api_key"
  }
}
HTTP statusTypical typeMeaning
400invalid_request_errorMalformed body, unknown model, invalid schema.
401authentication_errorMissing/bad API key.
403permission_errorKey lacks permission.
404not_found / invalid_request_errorUnknown endpoint or model.
429rate_limit_errorToo many requests; may include Retry-After.
500/502/503/504server_error / api_error / overloaded_errorUpstream failure; retryable.

What clients expect of a compatible server

  • Exact field names and nesting — clients parse choices[0].message.content, delta.tool_calls, and so on verbatim; renaming breaks them.
  • Correct object discriminators: chat.completion, chat.completion.chunk, list.
  • Proper SSE framing (data: ... + blank line, [DONE] terminator) with the standard content type.
  • Request messages echoed back faithfully — clients keep sending prior assistant/tool messages and expect the server to tolerate them.
  • Faithful finish_reason values and (ideally) usage.
  • Streaming and non-streaming paths both implemented; many clients silently default to streaming.
