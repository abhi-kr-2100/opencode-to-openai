The embeddings domain

An embedding is a compact list of numbers that captures what a piece of text means, produced by a model that is trained to place similar texts close together. This guide explains where those numbers come from, how machines decide that two texts are similar, what the numbers are useful for, and the wire contract of the /v1/embeddings API. It assumes no prior knowledge of machine learning: terms like pipeline, pooling, and L2 norm are defined the first time they appear.

What an embedding is

Send text to an embedding model and you get back a list of numbers — always the same length, no matter how long or short the text is: 

"the cat sat on the mat" → [ 0.021, -0.113, 0.004, …, 0.087 ]   (384 numbers)
"trains run on diesel"      → [ 0.211, -0.052, 0.133, …, -0.096 ]   (384 numbers)

The important thing is what the numbers mean. Think of each list as the address of the text in a map. The model was trained so that texts that say much the same thing occupy nearly the same address, and unrelated texts are far apart: 

"the cat sat on the mat"  ↔  "a cat was resting near the rug"   → very close
"the cat sat on the mat"  ↔  "I need to buy milk and eggs"      → very far

That single property — meaning maps to location — is the whole power of embeddings. It turns the question “is this text related to that one?” into a distance problem, which machines are good at. It also means the numbers record meaning, not spelling: cheap and inexpensive land near each other even though they share no letters, while cheap and cheep (one letter apart) do not.

A few pieces of vocabulary before going further:

  • Vector — one such list of numbers. “A vector of 384 numbers” means exactly that.
  • Dimension — one coordinate of the vector, i.e. one numbered position in the list. “384 dimensions” means each text is placed in a space with 384 independent directions of variation, and gets one coordinate along each.
  • Embedding model — the machine that performs the mapping from text to vector. It is a neural network of the same family that powers chat models, but it generates no words; it only outputs coordinates.

Finally, embeddings are deterministic: the same model always turns the same text into the same vector. This is what makes the whole workflow possible — documents can be embedded once and stored, and any later piece of text can be compared against them.

How text becomes a vector: the pipeline

Turning one piece of text into one vector is a fixed sequence of steps — the pipeline. Every embedding request runs through the same four stages, in this order:

Text
any length, any spelling
1 · Tokenize
split into tokens the model knows
2 · Encode
one provisional vector per token
3 · Mean pool
average the token vectors
4 · L2 normalize
shrink to unit length
Embedding
384 numbers, ready to compare

1. Tokenization — text becomes a list of tokens

A model does not read text character by character or word by word. It reads tokens: pieces of text from a fixed vocabulary the model was trained on (roughly word pieces — cat is one token, a long word may be several). The tokenizer splits the input into tokens and looks up each token’s numeric id in that vocabulary: 

"the cat sat on the mat"
        ↓ tokenize
      [the] [cat] [sat] [on] [the] [mat]     ← 6 tokens, in order
       791   3257  10432  525   791  23501    ← each token's vocabulary id (illustrative)

Tokenization is why batch requests (many texts in one call) are efficient, and it is where the model’s input limits come from: a “512 token limit” is a limit on the number of tokens, not the number of characters.

2. Encoding — one provisional vector per token

The model now reads the tokens in order and computes, for each token, a provisional vector of the full size. Six tokens produce a six-row table of numbers, one row per token: 

the    → [ 0.301, -0.120, 0.054, … ]        ┐
cat    → [ 0.922,  0.031, -0.308, … ]        │
sat    → [ 0.411,  0.288,  0.017, … ]        │  6 rows × 384 columns:
on     → [ 0.020, -0.156,  0.021, … ]        │  one 384-vector per token
the    → [ 0.301, -0.120, 0.054, … ]        │
mat    → [ 0.877,  0.140, -0.212, … ]        ┘

No row yet represents the whole sentence. Each row still belongs to one token, and its numbers depend on the token and its surroundings.

3. Mean pooling — many token vectors become one text vector

The model must produce one fixed-size vector no matter how many tokens the input had. Length differences cannot change the output size — a model’s dimension count is fixed forever. Mean pooling (a.k.a. average pooling) solves this: add the token rows together element-wise, then divide by the number of tokens: 

the + cat + sat + on + the + mat   (6 rows of 384 numbers)
                ÷ 6
        →  1 row of 384 numbers     ← the whole text's vector

Every token contributes to the average, so the sentence vector is a blend of all its words. Mean pooling is the standard choice for similarity-oriented models (some models use other strategies, such as the first token’s vector; the API contract here assumes mean pooling, matching OpenAI’s text-embedding-3 family).

4. L2 normalization — shrink the vector to unit length

A vector has a length — also called its L2 norm — computed from the numbers themselves: 

length = √(x₁² + x₂² + … + x₃₈₄²)        (square each number, add them up, take the root)

example:  vector (3, 4)
          length = √(3² + 4²) = √25 = 5
          normalized → (3/5, 4/5) = (0.6, 0.8)
          check: √(0.6² + 0.8²) = √1 = 1   ✓

L2 normalization divides every number of the vector by the vector’s length, so the result has length exactly 1. Why bother?

  • Length should carry no information. A long document should not get a “bigger” vector than a short sentence — only the direction in meaning-space should matter. Normalization guarantees that.
  • It enables a simple comparison formula. The similarity calculation below is only a plain multiplication when both vectors have length 1.

The vectors returned by the embeddings API are already normalized — clients can compare them directly without renormalizing, exactly as with OpenAI’s embedding endpoints.

Comparing embeddings: the dot product and cosine similarity

Once every vector has length 1, “how similar are two texts?” becomes one number. The dot product multiplies each pair of matching numbers and adds the results: 

similarity = (a₁·b₁ + a₂·b₂ + … + a₃₈₄·b₃₈₄) / (|a| · |b|)   ← cosine similarity

for normalized vectors |a| = |b| = 1, so the formula collapses to:

similarity = a₁·b₁ + a₂·b₂ + … + a₃₈₄·b₃₈₄                   ← just the dot product

This value — the cosine similarity — is the cosine of the angle between the two arrows, a number in the range −1 to 1:

Value What the arrows are doing Meaning for the texts
1 pointing the same way identical (or near-identical) meaning — achieved only by duplicate text
≈ 0.9 nearly the same way strongly related — paraphrases, answers, matching chunks
≈ 0.1 roughly perpendicular unrelated
−1 opposite ways opposite meaning; rare for real text

Concrete pairwise similarities for real-looking texts:

Pair Cosine similarity
“The cat sat on the mat.” / “A cat was resting near the rug.” 0.94
“The cat sat on the mat.” / “Trains run on diesel fuel.” 0.06
“Trains run on diesel fuel.” / “Rails and locomotives are being electrified.” 0.87
“A cat was resting near the rug.” / “Rails and locomotives are being electrified.” 0.11

The number is used in two standard ways:

  • Ranking: return the stored texts with the highest similarity to the query — this is nearest-neighbor search (“the top 5 matches”).
  • Thresholding: treat similarity above some cutoff (say 0.75) as “related” and everything below as “not” — good for deduplication and filtering.

A footnote for completeness: similarity can also be measured as the straight-line (Euclidean) distance between the points. For normalized vectors the two measures rank results identically, so vector stores may expose either and the outcomes agree.

What embeddings are for

Embeddings power everything where a program needs to find or group by meaning rather than by spelling:

  • Semantic search. Embed the query and each candidate document, return the nearest. Because matching happens in meaning-space, results need not share words with the query: “how do I renew my parking permit” finds a page titled “vehicle registration renewals”.
  • Retrieval-augmented generation (RAG). A chat model knows only what it was trained on; RAG hands it relevant context. A corpus is split into chunks, each chunk is embedded and stored; at query time the question is embedded, the closest chunks are retrieved, and those chunks are fed to a chat model together with the question:
Index time
documents → chunks → vectors → stored
Query time
question → its vector
Nearest neighbors
the k most similar stored chunks
Chat model
question + retrieved chunks → grounded answer
  • Clustering and deduplication. Nearly identical vectors correspond to nearly identical texts; group by closeness or drop the duplicates.
  • Classification. Embed a handful of labeled examples per category; a new text is classified by whichever example it is closest to.

These consumers all assume the same three guarantees: the vector size is fixed, the vectors are normalized, and similar meaning means a small angle (high cosine similarity).

The Embeddings API: POST /v1/embeddings

The OpenAI protocol has a second major endpoint beside Chat Completions. Where /v1/chat/completions generates text, /v1/embeddings converts text into vectors. The request and response are deliberately simple.

The request

POST /v1/embeddings

{ "model": "bge-small-en-v1.5",
  "input": "The cat sat on the mat.",
  "encoding_format": "float" }
Field Meaning
model The embedding model id. It must be an embedding model — one that produces vectors, never text. The id is validated against the configured model; unknown ids are rejected exactly like unknown model names on other endpoints.
input The text(s) to embed: a single string, or an array of strings. An array is a batch: all inputs are processed together in one forward pass and the vectors come back in the same order.
encoding_format "float" (default) returns the vector as ordinary JSON numbers; "base64" packs the same numbers into a compact string (typically about half the size over the wire for a 384-dimension vector).

Batching is the typical use: embed the chunks of a document (tens or hundreds of short texts) in a single request rather than one request per chunk.

The response

{
  "object": "list",
  "data": [
    { "object": "embedding", "index": 0, "embedding": [ 0.012, -0.034, … ] }
  ],
  "model": "bge-small-en-v1.5",
  "usage": { "prompt_tokens": 8, "total_tokens": 8 }
}
Field Meaning
data[].index Which input each vector answers to, starting at 0. With an array of n inputs there are n entries in order, so data[i] is the vector for input[i].
data[].embedding The vector itself: the model’s normalized coordinates, as floats or base64 depending on encoding_format.
usage.prompt_tokens, total_tokens Token counts for reading the inputs (the sum of the inputs’ token counts). Embeddings generate nothing, so there are never completion tokens.

Responses are always one-shot: no streaming, no partial results. Clients wait for the full JSON body and store or compare the vectors.

Embeddings vs. Chat Completions

Chat Completions Embeddings
Output generated text (and tool calls) a fixed-size vector (or vectors)
Input a conversation: roles, content parts, tools plain text (single string or array)
Nature generative and sampled — slight run-to-run variation deterministic — same text, same vector, always
Delivery single JSON body or SSE stream single JSON body only
Usage prompt + completion tokens prompt tokens only
What the client does with it reads the text stores it, and/or compares it by dot product

Embedding models at a glance

Embedding models are small by LLM standards — tens of millions of parameters versus the hundreds of billions of frontier chat models — which is exactly why one can run on a single machine. Their quality is measured on retrieval benchmarks: given a corpus and a set of queries, how often does nearest-neighbor search return the relevant documents? The dimension count, token budget, and language coverage are fixed properties that consumers must design around:

Model Dims Max tokens Size (quantized) Notes
all-MiniLM-L6-v2 384 256 ~25 MB The classic smallest; the baseline every small model is compared against.
bge-small-en-v1.5 384 512 ~33 MB Strong English retrieval for its size; the configured default.
gte-small 384 512 ~33 MB Marginal edge on general English benchmarks; trained on multilingual data.
snowflake-arctic-embed-s 384 512 ~33 MB Retrieval-first training; among the best retrievers at this size.
mxbai-embed-xsmall-v1 384 512 ~33 MB Matryoshka model: the first n dimensions may be used alone (see below).
bge-base-en-v1.5 768 512 ~110 MB ~3× the weight and twice the dimensions; only where quality demands more.

Three properties in that table matter to every consumer:

  • The token budget is a design constraint. Text beyond the budget is truncated — the excess never reaches the model and contributes nothing to the vector. Documents destined for retrieval must therefore be split into chunks that fit (RAG pipelines are built around this).
  • The dimension count is a contract. A vector store is built for one dimension count. Every vector returned by a given model has exactly that many numbers — and switching to a model with a different count invalidates previously stored vectors. (Some models, marked as matryoshka, allow deliberately keeping only the first n dimensions to trade quality for space.)
  • Models may be quantized. The same model can be stored at reduced number precision (q8): roughly one third of the file size for a barely measurable quality drop. Quantized artifacts are the standard choice for local use — the sizes above are the quantized ones.

Where embeddings run

Of the three domains in this documentation set, embeddings are the one that crosses no bridge. Chat requests are proxied — an adapter passes them to OpenCode, which runs the agentic loop. Embeddings cannot be proxied: OpenCode exposes no embedding capability. Instead the adapter serves the embeddings endpoint itself, with a small model loaded into its own process:

OpenAI client
POST /v1/embeddings
Adapter
validates, batches, runs the pipeline
Embedding model
local, in-process, CPU
Client
a 384-number vector per input

The practical consequences of local embedding, which clients should expect:

  • Nothing leaves the machine. There is no external embedding service, no API key, and no data egress — every text is processed on the host’s own CPU. No GPU is required.
  • First use needs a download. Before the model can run it must be fetched once from the model hub and cached on disk (tens of MB). Subsequent starts load from that cache.
  • Cold start. The very first request of a fresh process may take seconds (download, load, warm-up) — a cold start, not a stall. The server can optionally preload the model at startup so even the first request is fast. Once loaded, the model stays resident in memory and is shared by all requests; each short text costs milliseconds.
  • Requests queue on the model. Embeddings are computed one batch at a time; a request that arrives mid-batch waits its turn, and a long batch delays the next.
  • Vectors are model-specific. They are deterministic for a given model version, but a model upgrade can move every vector; stores must be re-embedded. Clients should treat vectors as belonging to the model id that produced them — which is why the response echoes it.

Glossary

Embedding Embeddings

The vector a model produces for a piece of text: a fixed-length list of numbers where meaning is distance. Texts that mean the same thing are close; unrelated texts are far apart.

Example — the whole idea in one picture

Vector, dimension Embeddings

A vector is the list of numbers; a dimension is one numbered slot in that list. A “384-dimension vector” has 384 slots. A model’s dimension count never changes, however long the input text is.

Example — 384 slots, here shown as five
[ 0.021, -0.113, 0.004, …, 0.087 ]
   ↑1     ↑2     ↑3        ↑384
Token / tokenizer Embeddings

Tokens are the vocabulary pieces a model actually reads (roughly word parts). The tokenizer converts text into an ordered list of token ids. “512 tokens” is the model’s input budget — anything beyond it is dropped.

Example — text → tokens
"the cat sat" → [the] [cat] [sat] → 3 tokens
Forward pass Embeddings

One run of the model over its input. An embedding is the output of one forward pass, and a batch of many texts is handled in one forward pass — which is why batching is cheap.

Mean pooling Embeddings

Averaging the token vectors (add the rows, divide by the token count) so texts of any length yield one fixed-size vector. This is the stage that discards length and keeps blended content.

L2 norm / normalization Embeddings

The length of a vector — the root of the sum of its squared numbers. Normalization divides every number by that length so the vector has length exactly 1, making only its direction meaningful and enabling the simple dot-product comparison. All returned vectors are already normalized.

Example — rescaling to unit length
(3, 4) → length √25 = 5 → (0.6, 0.8) → length √1 = 1
Dot product / cosine similarity Embeddings

The comparison: multiply matching numbers, add them up. For normalized vectors this equals the cosine of the angle between the two vectors, in the range −1 (opposite) to 1 (identical), with ~0 meaning unrelated.

Example — same direction scores 1, perpendicular scores 0
(0.6, 0.8) · (0.6, 0.8) = 0.36 + 0.64 = 1.00
(0.6, 0.8) · (−0.8, 0.6) = −0.48 + 0.48 = 0.00
Nearest-neighbor search / vector store Embeddings

The application pattern: pre-embed a corpus, store the vectors, and answer “which stored texts are closest to this new vector?” A vector store (vector database) is software engineered precisely for that query.

Truncation Embeddings

Cutting input at the model’s token budget (512 here). The cut portion is ignored — the vector reflects only what fit. Truncation happens with a warning rather than a rejection; retrieval pipelines should chunk documents so chunks fit.

Quantization Embeddings

Storing the model’s numbers at reduced precision to shrink its file size — the quantized variant of a model is typically about one third of the full-precision size, at a barely measurable quality cost. The standard format for local, in-process models.

Cold start Embeddings

The latency of the first embeddings request in a fresh process: model download (once per machine), load, and warm-up. Later requests are milliseconds. Preloading the model at startup moves the cold start before the server is ready to serve.
