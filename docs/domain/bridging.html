Overview OpenCode OpenAI v1 API Bridging

Bridging the two domains

An adapter that exposes OpenCode behind the OpenAI v1 protocol is a translation layer between two data models. This guide lays out the conceptual map — what maps cleanly, what requires synthesis, and where the translation is inherently lossy — so an implementation can be shaped deliberately.

The shape of the problem

Both systems ultimately do the same thing — maintain a conversation, invoke a model, surface tool calls — but they express it differently:

DimensionOpenCodeOpenAI v1
Conversation unit Session (server-side state, owns history) Stateless request: client resends the full messages array
Content model Typed parts inside messages String or typed content parts inside messages
Tool execution Server executes tools; results stream back as part states Client executes tools; results returned as new tool messages
Streaming SSE event bus (message.part.updated deltas) SSE completion chunks (choices[].delta)
State reporting Session statuses, permission requests, todos, snapshots Only the completion itself (plus errors)

The central insight: the adapter is the agentic loop for the OpenAI side. OpenAI clients send one request and expect one (streamed) completion; OpenCode runs a multi-step agent loop in the background. The adapter must either translate the whole loop into one response or expose the loop’s steps in OpenAI’s vocabulary.

Concept map

reasoning part reasoning_content in deltas / assistant messages Partial. Only some models/clients expose reasoning; often dropped.
file part image_url / content part for the media type Partial — URLs vs base64, mime coverage, audio/video support varies by model.

The tool-call translation, in detail

OpenCode executes tools itself; OpenAI hands them to the client. The adapter sits in the middle:

  1. Outbound (OpenCode → OpenAI client): a tool part with state pending/running becomes an assistant tool_calls entry in the streamed or final response. The callID maps to the tool call id; tool maps to function.name; input maps to function.arguments (serialized to a JSON string).
  2. Inbound (client → OpenCode): the adapter must execute the call. Two strategies:
    • Proxy OpenCode’s own tools: declare them in tools, translate the client’s function call into a prompt-style invocation, and feed results back as new user/context. Simple, but the agent loop then runs on top of the OpenAI client’s own loop.
    • Let OpenCode run the loop: let OpenCode’s internal tool use happen, then translate each completed/errored tool part back into a tool_calls + tool message pair for the client, ending when OpenCode finishes. This preserves agentic behavior but presents it as ordinary tool calling to the client.
  3. Tool results (OpenCode → client): a completed tool part’s output (and error for failed calls) maps to the tool role message content, keyed by tool_call_id.

Streaming translation

The two streaming models map event-by-event:

OpenCode eventOpenAI chunk
message.part.updated — text part, with deltadelta.content
message.part.updated — reasoning partdelta.reasoning_content (or dropped)
message.part.updated — tool part, pending/runningassistant message start (delta.role) + delta.tool_calls entry with id/name
message.part.updated — tool part, completed/errorNo chunk; the result belongs to a later tool message round. An adapter driving the full loop emits the tool_calls finish_reason instead.
session.idleFinal chunk with finish_reason and usage
session.error / message errorError chunk or aborted stream

The ordering contract of the OpenAI protocol must be preserved: role delta first, then content, then (optionally) tool-call deltas, then finish_reason. OpenCode events carry no such ordering guarantee, so the adapter must buffer and re-sequence.

The agentic loop mismatch

OpenCode run
model → tools (server-side) → model → tools → … → text reply — one assistant message, many steps
OpenAI request
model → tool_calls (client-side) → tool messages → model — one request per round, loop owned by the client

This mismatch drives every design decision:

  • One-shot mode: OpenCode’s whole run maps to one OpenAI completion. Every tool OpenCode executed appears in the single response’s tool-call history (assistant tool_calls + tool results). The final text is the completion’s content. Clients that iterate tool calls will simply have nothing left to execute — a fine outcome for chat-style usage.
  • Iterative mode: each OpenCode step is surfaced as one response, and the client’s tool-result round trip drives the next step. This preserves interactivity but means one OpenCode run spans multiple OpenAI requests.

Gaps and lossy translations

  • Steps vs rounds. OpenCode’s step boundaries (which include tool execution internally) have no OpenAI equivalent; only the tool-call boundary is representable.
  • Subagents. When OpenCode’s primary agent delegates to a subagent (a subtask part in a child session), an OpenAI client sees nothing — or, in one-shot mode, a task-style tool call whose results are already folded in.
  • Permissions. ask-gated tools pause the run awaiting a human. An adapter must decide policy up front: configure allow/deny, or surface the pending permission as a tool result explaining the denial.
  • Compaction. History shrinks mid-session without client awareness. Clients that echo history back (OpenAI’s stateless model) may briefly disagree with the session; adapters should reconcile from the session, not from client-supplied history.
  • Reasoning output. OpenCode reasoning parts map to reasoning_content only for models/clients that support it; otherwise they must be suppressed.
  • Cost. OpenCode tracks dollar cost and cache token details that the OpenAI usage object cannot express exactly; the mapping is an approximation.
  • Session statefulness. OpenAI clients are stateless; OpenCode sessions are stateful. If a client sends a partial or modified history, the adapter must choose the source of truth (usually: trust the session, treat the client’s messages as the current turn).
  • Concurrency. One session is busy while the agent runs; a second request to the same conversation must be queued, rejected, or routed to a fresh session.

Design guidance for an adapter

  • Expose GET /v1/models from OpenCode’s provider/model discovery so clients can list what they may request.
  • Map the model string to providerID/modelID deterministically, and reject unknown models with a standard 400 error.
  • Implement both streaming and non-streaming from the same underlying event-driven flow; emit SSE chunks only when stream: true.
  • Preserve the OpenAI wire contract strictly (field names, object discriminators, chunk ordering, [DONE], usage) — see the client expectations section of the OpenAI guide.
  • Handle aborts: a client disconnecting mid-stream should abort the OpenCode session so the agent stops working.
  • Keep the translation in one place: an internal, normalized representation of “a turn” that both domains are rendered into and out of.
