Compatibility Guide

OpenAI API Compatibility & Limitations

This document details how OpenAI Chat Completion (v1) API features map to the underlying OpenCode session engine. Since opencode-to-openai bridges a stateful, agentic local engine with a stateless chat completion protocol, certain options are emulated, some have partial/lossy translation, and many generation options are bypassed during API interaction.

Core Mismatch Notice

The OpenAI protocol is completely stateless (the client resends the entire history on every request). OpenCode sessions are server-side, stateful, and run their own multi-step agent loops. The adapter is responsible for bridging these two paradigms by mapping client parameters, emulating tools, and flattening conversational history.

Feature & Parameter Matrix

messages Emulated / Lossy Since OpenCode starts a fresh session and cannot natively replay prior turns, the adapter flattens all preceding turns (including past tool calls and results) into a single transcript part formatted with role headers (e.g. user:, assistant:, tool:) which is pre-pended to the active prompt.
stream Emulated Synthesized at the adapter layer. OpenCode’s session.prompt is executed to completion, and then the adapter splits the resulting completion into incremental standard SSE completion chunks (including fragmented tool arguments and role-only preamble).
tools Emulated Declares userspace tools. Translated into an emulated markdown prose section injected into the system prompt, instructing the model to output tool invocations in <tool_call>...</tool_call> tags. Native OpenCode session tools are bypassed.
tool_choice Emulated Enforced via prompt engineering. "none" forces a no-tools instruction; "required" forces the model to use at least one tool; specific functions force the exact tool. Throws 400 Bad Request if tool_choice is specified but tools are omitted/unknown.
stream_options Supported Supports include_usage: true by appending a dedicated usage chunk with empty choices at the end of the SSE stream.
temperature Ignored Validated (0–2) but omitted from prompt requests. OpenCode uses the underlying model/agent default configurations.

max_tokens Ignored Validated but completely ignored. OpenCode utilizes model default or context/output configuration caps.
n Ignored Validated but ignored. The adapter always generates and returns exactly 1 completion candidate (index: 0).

In-Depth Details & Seams

1. Conversational History & Transcript Flattening

An OpenAI client assumes the model is a stateless text predictor. It sends the entire chat history in every request. In contrast, OpenCode creates a server-side session.

To reconcile this, the adapter flattens all conversational history (up until the final user/tool message) into a single text transcript part. This transcript format labels turns with role markers: 

user: Can you help me investigate the flaky test?

assistant: I can certainly run the test suite for you.
<tool_call>{"name": "bash", "arguments": "{\"command\":\"bun test\"}"}</tool_call>

tool (call_12345): FAIL - test/flaky.test.ts timed out

Because this transcript is passed to OpenCode as a single text part, the model views the history as a flat preamble rather than native historical turns.

2. Emulated Function/Tool Calling

OpenAI supports native tool-calling JSON structures, whereas OpenCode runs its own agentic tools server-side. The adapter emulates OpenAI-compatible function calling by doing the following:

  • Injects detailed prose definitions of the client-supplied tools into the system prompt.
  • Requires the model to request tools via a raw XML-like string payload block: <tool_call>{"name": "...", "arguments": ...}</tool_call>.
  • Intercepts and strips these emulated tool blocks from the textual content response before returning it to the OpenAI client.
  • Surfaces the parsed blocks in the standard choices[0].message.tool_calls array.

3. Multi-Modality & Vision Support

OpenAI Chat Completions support rich array-based content parts. opencode-to-openai maps these as follows:

  • Text Parts: Passed directly through to OpenCode as standard text parts.
  • Image URL Parts: Mapped to OpenCode file parts. The adapter automatically detects the MIME type from data URLs or defaults to application/octet-stream for plain HTTP URLs.
  • Other Parts (Audio, Video, etc.): Not supported. If encountered, they trigger a 400 Bad Request error.

4. Token Accounting and Usage Mapping

OpenCode tracks token consumption with fine-grained counts, including input, output, reasoning, and cache reads/writes. The adapter consolidates these counts to fit OpenAI’s standard usage model:

  • prompt_tokens = OpenCode input + cache.read + cache.write
  • completion_tokens = OpenCode output + reasoning
  • total_tokens = prompt_tokens + completion_tokens
